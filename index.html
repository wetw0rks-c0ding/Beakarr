Import Flow
4 schermate + API sequence: browse → folder → match → progress · v3 (Radarr/Sonarr) · v1 (Lidarr)
Sequenza schermate
SchermataRouteTrigger
Import Browse/import/browseTap icona download-tray in Activity AppBar → bottom sheet servizio
Import Folder/import/folderTap cartella nel tree + CTA "Select Folder"
Import Match/import/matchTap "Import X files" → analisi già pronta (eager fetch)
Import Progress/import/progressTap "Confirm Import" → submit + polling
Il global importService ('radarr'|'sonarr'|'lidarr') è settato dal bottom sheet e consumato da tutte e 4 le schermate. In Flutter usa un InheritedWidget o Riverpod StateProvider. Il prefisso API (v3 per Radarr/Sonarr, v1 per Lidarr) viene risolto dall'ApiClient in base a questo flag.

Future<List<ManualImportItem>> fetchItems(String folderPath) =>
  api.get(
    '/manualimport',
    queryParams: {
      'folder': folderPath,
      'filterExistingFiles': 'true',    // nasconde i file già in libreria
    },

// Radarr:  folder, downloadId, movieId,                     filterExistingFiles
// Sonarr:  folder, downloadId, seriesId, seasonNumber,      filterExistingFiles
// Lidarr:  folder, downloadId, artistId, filterExistingFiles, replaceExistingFiles

// Risposta — List<ManualImportResource> — campi comuni:
// { id, path, name, size, quality:QualityModel, qualityWeight,
//   languages:Language[], releaseGroup, downloadId, indexerFlags,
//   customFormats:CustomFormatResource[], customFormatScore,
//   rejections: [{ reason:String, type:'permanent'|'temporary' }] }

// Campi specifici per servizio:
// Radarr:  + relativePath, folderName, movie:MovieResource,    movieFileId
// Sonarr:  + relativePath, folderName, series:SeriesResource,  seasonNumber,
//           episodes:EpisodeResource[], episodeFileId, releaseType
// Lidarr:  + artist:ArtistResource, album:AlbumResource, albumReleaseId,

Quando un file è "non matchato"? Il match è null (movie==null per Radarr, series==null o episodes==[] per Sonarr, album==null per Lidarr) e/o ha rejections con type:'permanent'. Le rejections 'temporary' sono spesso non bloccanti (es. file ancora aperto da un altro processo) — l'import può comunque essere tentato.

Perché serve il reprocess? Senza chiamare POST /manualimport dopo il Fix, mandi al server un movieId diverso ma con quality/languages/customFormats non ricalcolati per quel nuovo target — l'import può fallire o produrre rejections inaspettate. Il reprocess è cheap (no I/O su disco) e deve essere considerato parte del flusso Fix.
Submit Strategy — UNICA per Radarr/Sonarr/Lidarr http · dio
Tutti e tre i servizi usano lo stesso pattern: POST /command {name:"ManualImport", files:[ManualImportFile], importMode} → ritorno asincrono → polling su GET /command/{id}. Una sola classe ImportSubmitter, le differenze sono solo nei campi del payload files[].
ServizioEndpoint triggerRispostaPolling
RadarrPOST /api/v3/commandAsync — CommandResource {id, status:"queued", ...}Sì — GET /api/v3/command/{id}
SonarrPOST /api/v3/commandAsync — CommandResource {id, status:"queued", ...}Sì — GET /api/v3/command/{id}
LidarrPOST /api/v1/commandAsync — CommandResource {id, status:"queued", ...}Sì — GET /api/v1/command/{id}
// lib/services/import_submitter.dart
// UNICA implementazione — il payload `files[]` cambia per servizio.

class ImportSubmitter {
  final ApiClient api;
  final String service; // 'radarr'|'sonarr'|'lidarr'

  Future<int> submit(List<ManualImportItem> items, {
    String importMode = 'auto',    // 'auto' | 'move' | 'copy'
  }) async {
    final body = {
      'name':       'ManualImport',
      'importMode': importMode,
      'files':      items.map(_toFile).toList(),
    };
    if (service == 'lidarr') {
      body['replaceExistingFiles'] = false;
    }
    final res = await api.post('/command', body: body);
    return res['id'] as int;   // commandId per il polling
  }

  Map<String, dynamic> _toFile(ManualImportItem i) {
    switch (service) {
      case 'radarr': return {
        'path': i.path,                  'folderName': i.folderName,
        'movieId': i.movie!.id,
        'quality': i.quality,             'languages': i.languages,
        'releaseGroup': i.releaseGroup,  'indexerFlags': i.indexerFlags,
        'downloadId': i.downloadId,
      };
      case 'sonarr': return {
        'path': i.path,                  'folderName': i.folderName,
        'seriesId': i.series!.id,
        'episodeIds': i.episodes!.map((e) => e.id).toList(),
        'episodeFileId': i.episodeFileId,
        'quality': i.quality,             'languages': i.languages,
        'releaseGroup': i.releaseGroup,  'indexerFlags': i.indexerFlags,
        'releaseType': i.releaseType,    'downloadId': i.downloadId,
      };
      case 'lidarr': return {
        'path': i.path,
        'artistId': i.artist!.id,
        'albumId': i.album!.id,         'albumReleaseId': i.albumReleaseId,
        'trackIds': i.tracks!.map((t) => t.id).toList(),
        'quality': i.quality,             'indexerFlags': i.indexerFlags,
        'downloadId': i.downloadId,
        'disableReleaseSwitching': i.disableReleaseSwitching,
      };
    }
    throw UnsupportedError(service);
  }
}
Vantaggio rispetto al design precedente: niente strategia polimorfica, niente ImportResult.sync() vs ImportResult.async(). La schermata Progress fa sempre polling; per i Radarr/Sonarr l'unica differenza è che il command termina più in fretta (no transcoding, no metadata refresh aggiuntivo).

// Polling stream — Timer.periodic ogni 2 s
Stream<CommandResource> pollCommand(int commandId) async* {
  while (true) {
    final data = await api.get('/command/$commandId');
    final cmd  = CommandResource.fromJson(data);
    yield cmd;
    if (cmd.isTerminal) break;
    await Future.delayed(const Duration(seconds: 2));
  }
}

// CommandResource — campi rilevanti:
// {
//   id, name, commandName, message,
//   status:   'queued'|'started'|'completed'|'failed'|'aborted'|'cancelled'|'orphaned',
//   priority: 'normal'|'high'|'low',
//   trigger:  'unspecified'|'manual'|'scheduled',
//   queued, started, ended:    DateTime? (ISO string),
//   duration:                  String? (es. "00:00:03.4521234"),
//   exception:                 String?  (popolato se status==failed),
//   sendUpdatesToClient: bool, // ManualImport ha sempre true
//   stateChangeTime, lastExecutionTime, clientUserAgent,
// }

extension on CommandResource {
  bool get isTerminal => const {
    'completed', 'failed', 'aborted', 'cancelled', 'orphaned'
  }.contains(status);
}
Granularità per-file: il CommandResource NON espone l'esito per singolo file. Per ricostruire la per-file list con ✓/✗ devi:
1. tenere in memoria la lista files[] originariamente inviata,
2. dopo il completed, fare un GET /history?eventType=downloadFolderImported filtrato per downloadId (o per timestamp >= cmd.started) per vedere quali file sono stati effettivamente importati,
3. tutto ciò che non compare nella history è "failed" / "skipped" — il motivo si ricava dal log di cmd.exception o da GET /log/file.
Se questa complessità è troppa per la prima release, mostra solo lo stato globale del command (queued/started/completed/failed) + il count finale.
Se status==failed, il messaggio di errore è in cmd.exception (string multilinea, può essere lungo — wrappa in ExpansionTile).

// lib/services/api_client.dart
class ApiClient {
  final String baseUrl;     // es. https://radarr.lan
  final String apiKey;
  final String apiVersion;  // 'v3' o 'v1' — da Settings

  String _full(String p) => '$baseUrl/api/$apiVersion$p';
  Map<String, String> get _h => {'X-Api-Key': apiKey};

  Future<dynamic> get(String p, {Map<String, dynamic>? queryParams}) =>
    http.get(Uri.parse(_full(p)).replace(queryParameters: queryParams), headers: _h)
      .then((r) => jsonDecode(r.body));

  Future<dynamic> post(String p, {dynamic body}) =>
    http.post(Uri.parse(_full(p)),
              headers: {..._h, 'Content-Type': 'application/json'},
              body: jsonEncode(body))
      .then((r) => jsonDecode(r.body));
}

);
